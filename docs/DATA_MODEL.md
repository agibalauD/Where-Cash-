# Модель данных и расчёты

## ExpenseRecord

| Поле | Тип | Назначение |
|---|---|---|
| `id` | `UUID` | Уникальный идентификатор операции |
| `amountMinor` | `Int64` | Сумма в копейках/центах |
| `currencyRaw` | `String` | `BYN` или `USD` |
| `categoryRaw` | `String` | Стабильное значение категории |
| `createdAt` | `Date` | Дата и время добавления |
| `bynPerUSD` | `Double?` | Снимок курса BYN за 1 USD |
| `rateDate` | `Date?` | Дата использованного курса |
| `usedStaleRate` | `Bool` | Признак использования сохранённого курса |

Деньги хранятся как целое число минимальных единиц: `12,50 BYN` сохраняется как `1250`. Это исключает накопление двоичных погрешностей при сложении.

## SavingsGoal

| Поле | Тип | Назначение |
|---|---|---|
| `id` | `UUID` | Уникальный идентификатор цели |
| `name` | `String` | Пользовательское название |
| `targetMinor` | `Int64` | Целевая сумма в минимальных единицах |
| `currencyRaw` | `String` | Валюта цели BYN/USD |
| `createdAt` | `Date` | Дата создания |

Валюта фиксируется после первого пополнения. Название и целевую сумму можно менять; завершённость вычисляется как `накоплено >= цель` и отдельно не хранится.

## SavingsContribution

| Поле | Тип | Назначение |
|---|---|---|
| `id` | `UUID` | Уникальный идентификатор пополнения |
| `goalID` | `UUID` | Идентификатор цели |
| `amountMinor` | `Int64` | Исходная сумма пополнения |
| `currencyRaw` | `String` | Исходная валюта BYN/USD |
| `createdAt` | `Date` | Дата добавления |
| `bynPerUSD` | `Double?` | Снимок курса для пересчёта |
| `rateDate` | `Date?` | Дата курса |
| `usedStaleRate` | `Bool` | Использовался ли кэшированный курс |

Пополнения не являются `ExpenseRecord` и не участвуют в расходных итогах. При удалении цели её пополнения удаляются вручную в одной операции контекста.

## Период аналитики и архив

Дата начала активной аналитики хранится как Unix timestamp в `UserDefaults` по ключу `analyticsStartTimestamp`. Значение `0` означает, что учитывается вся история.

- `ExpenseRecord.createdAt` раньше границы считается архивным;
- архивные расходы сохраняются в SwiftData и отображаются в истории;
- архив исключён из диаграммы, итогов, категорий, месячного лимита и Telegram-статистики;
- операции после границы участвуют в расчётах обычным образом;
- `SavingsGoal` и `SavingsContribution` не фильтруются по этой границе.

Сброс не изменяет схему SwiftData и не выполняет массовое обновление записей: архивный статус вычисляется по дате, поэтому операция быстрая и сохраняет исходные данные.

## Категории

Порядок категорий стабилен и используется в легенде и диаграмме:

1. `food` — Еда, зелёный;
2. `transport` — Транспорт, синий;
3. `entertainment` — Развлечения, фиолетовый;
4. `purchases` — Покупки, оранжевый.
5. `other` — Прочие расходы, розовый.
6. `savings` — прежний служебный raw value накоплений; сохраняется для совместимости, но новый интерфейс маршрутизирует пополнение напрямую по UUID цели.

Для диаграммы и расходных итогов используется `ExpenseCategory.spendingCases`, поэтому «Накопления» не создают отдельный сектор.

## Валютная логика

- Сумма в исходной валюте никогда не изменяется.
- Для USD → BYN: `USD × bynPerUSD`.
- Для BYN → USD: `BYN ÷ bynPerUSD`.
- Результат округляется до ближайшей минимальной единицы валюты.
- Если исходная и целевая валюты совпадают, курс не требуется.
- Если для смешанного набора нет курса хотя бы у одной необходимой операции, соответствующая агрегированная сумма считается недоступной и показывается как `—` или `Курс недоступен`.

Источник — `https://api.nbrb.by/exrates/rates/USD?ondate=YYYY-MM-DD&parammode=2`. Ответ декодируется по полям `Cur_OfficialRate` и `Date`.

Последний успешный курс сохраняется в `UserDefaults`. При ошибке сети он используется повторно с признаком устаревания. Если кэша ещё нет, операция сохраняется без курса и остаётся корректной в исходной валюте.

Пополнение в валюте цели не требует курса. Пополнение в другой валюте допускается только при наличии актуального или последнего кэшированного курса; без курса оно не сохраняется.

## Месячная статистика

- Месяц определяется системным календарём и часовым поясом пользователя.
- Операции фильтруются по месяцу `createdAt`.
- Для каждой категории рассчитывается сумма в текущей основной валюте.
- Кольцевая диаграмма строится только когда все необходимые пересчёты доступны и есть хотя бы одна ненулевая сумма.
- Нулевые категории остаются в списке, но не образуют сектор.
- Для пустого или неполностью пересчитываемого месяца отображается нейтральное кольцо.
- Внешнее кольцо рассчитывает отношение расходного итога выбранного месяца к повторяющемуся лимиту и ограничивает визуальное заполнение значением 100%.
- Цвет интерполируется по точкам: индиго 0%, синий 30%, жёлтый 50%, красный 80% и выше.
- Прогресс каждой из одной или двух выбранных целей использует все её пополнения независимо от выбранного месяца.
- Telegram-карточка использует те же расчёты, но всегда фильтрует расходы по текущему календарному месяцу. Идентификатор выбранного месяца для бота не хранится.

## Настройки

| Ключ | Значение по умолчанию | Назначение |
|---|---|---|
| `lastCurrency` | `BYN` | Последняя валюта ввода и основная валюта статистики |
| `showSecondaryCurrency` | `true` | Показывать второй общий итог |
| `telegramOwnerUserID` | отсутствует | Telegram user ID единственного привязанного владельца |
| `telegramChatID` | отсутствует | Идентификатор разрешённого личного чата |
| `telegramLastUpdateID` | отсутствует | Последнее обработанное обновление для защиты от повторов |
| `telegramBotUsername` | отсутствует | Имя проверенного бота для отображения в настройках |
| `monthlyLimitMinor` | отсутствует | Повторяющийся месячный лимит в минимальных единицах |
| `monthlyLimitCurrency` | `BYN` | Валюта месячного лимита |
| `selectedSavingsGoalID` | отсутствует | Один или два UUID через запятую для главного экрана и новых пополнений; одиночный UUID старых версий остаётся допустимым |
| `analyticsStartTimestamp` | `0` | Момент начала активного периода; более ранние расходы являются архивными |

Автозапуск хранится и управляется самой системой через `SMAppService`, а не в `UserDefaults`.

Токен Telegram не относится к обычным настройкам и хранится отдельным generic-password элементом в macOS Keychain. Незавершённая Telegram-операция существует только в памяти. Бот создаёт `ExpenseRecord` для расходной категории или `SavingsContribution` для UUID цели, переданного кнопкой с её названием.
